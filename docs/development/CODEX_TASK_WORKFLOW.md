## 权威范围

本文件是 RECA 中任务理解、范围控制、计划、实施顺序、不确定性处理和交付说明的详细开发规则。仓库级红线仍以 [AGENTS.md](../../AGENTS.md) 为准。

## 不负责的内容

本文件不定义产品需求、数据字段、API 契约、测试指标、安全政策或里程碑范围。

## 1. 任务开始

收到任务后先完成以下检查：

1. 识别用户要求的动作：分析、诊断、修改、验证、提交或等待。
2. 明确允许修改和禁止修改的路径。
3. 读取根 `README.md`、`AGENTS.md` 和对应领域权威文档。
4. 检查当前分支、HEAD、tag、工作树和未追踪文件。
5. 检查实际代码、迁移、Compose、CI 和测试，不只根据文档推断。
6. 找出任务涉及的需求 ID、Schema、API、枚举、状态和里程碑。
7. 记录不能改变的不变量和完成条件。

对于文档任务，还必须确认：

- 哪个文件是唯一权威；
- 内容是保留、移动、摘要、去重还是归档；
- 是否存在稳定标题、ID、锚点或外部链接；
- 历史材料是否明确为非权威；
- 移动后是否仍能从入口到达。

对于开源集成任务，还必须按顺序完成：

```text
Read research record
→ Verify pinned commit
→ Verify license
→ Run minimal spike
→ Compare with fallback
→ Choose boundary
→ Implement
→ Run upstream-adapted tests
→ Update attribution
→ Record limitations
```

对应来源研究和 ADR 是任务输入，不是“已集成”证明。Spike 必须使用目标环境和主案例验证效果、失败、资源和离线能力；只有边界与许可证决策完成后才修改依赖、Compose、Vendor 或运行时。

## 2. 范围控制

最小改动不是最少文件，而是完成请求所需的最小语义范围。

- 不修改用户明确排除的文件；
- 不顺手修复无关缺陷；
- 不借重构删除需求或降低测试标准；
- 不提前实现后续里程碑；
- 不新增无必要抽象、顶级目录或依赖；
- 不把计划结构机械创建为空目录；
- 不把历史文档恢复为正式需求来源。

当任务跨越多个权威领域时，先列出每个领域的变更和验证，再按依赖顺序实施。

## 3. 计划原则

实质性任务建议按以下结构组织：

```text
事实核验
→ 不变量与风险
→ 最小实现切面
→ 编辑或编码
→ 定向验证
→ 跨文档或跨层验证
→ Git 差异检查
→ 交付说明
```

计划必须区分：

- 已完成；
- 正在执行；
- 尚未开始；
- 因外部决定阻塞。

不能把尚未验证的步骤标记为完成。

## 4. 实施顺序

业务开发默认顺序：

```text
需求和契约
→ 领域模型
→ 数据库约束和迁移
→ Repository / Service
→ 按需选择 Direct Library / Adapter / Isolated Service
→ Tool
→ 测试
→ API
→ 前端
→ Agent
```

具体任务可以省略不涉及的层，但不得反转关键边界：

- Agent 不得先于确定性工具；
- Tool 不得绕过 Service；
- API 不得先定义与权威契约冲突的形状；
- 前端不得发明后端状态；
- 高风险执行不得先于 `ApprovalRecord`；
- 正式 Agent 不得早于 M8。

只读、扫描、候选生成和预览不因使用 AI 或 Tool 而自动升级为正式审批。复用第三方能力前必须核验许可证、固定上游版本、建立来源与归属记录；无需替换、隔离或复杂转换的小型稳定库不强制增加 Adapter。

选择边界时记录直接库、Provider/Adapter、独立/隔离服务、选择性 Vendor、资源快照、设计参考或延期的理由。实现完成后必须同步固定版本、实现元数据、输出转换、回退、上游改造测试来源、`THIRD_PARTY_NOTICES.md`（仅实际纳入时）和已知限制。

## 5. 工作树保护

工作树可能包含用户或其他任务的修改。

- 开始前执行 `git status --short`；
- 不使用 `git reset --hard` 或破坏性 checkout；
- 不回滚不属于当前任务的差异；
- 同一文件存在既有修改时，先阅读并在其基础上编辑；
- 无法区分来源时，保持差异并在交付中说明；
- 提交时只暂存当前任务明确拥有的修改；
- 如果入口文件与既有修改重叠，不能为了生成干净 commit 而覆盖它们。

## 6. 不确定性处理

可以自行决定：

- 与现有模式一致的局部命名和排版；
- 不改变契约的可逆实现细节；
- 与任务直接相关的定向测试；
- 明显的链接、拼写或结构修复。

必须请求决定：

- P0/P1 范围变化；
- 根许可证选择；
- 敏感数据外发或新增外部 Provider；
- 安全、权限或项目隔离放宽；
- API、Schema、Tool、枚举或状态的破坏性变化；
- 需求语义或成功指标变化；
- 删除历史、迁移或用户数据；
- materially different 的产品行为。

请求决定前先穷尽只读核验，并清楚说明现状、冲突、可选方案和影响。

## 7. 文档同步

发生以下变化时同步对应权威文档：

| 变化 | 文档 |
| --- | --- |
| 产品范围、需求或优先级 | `docs/PRODUCT_REQUIREMENTS.md` |
| 架构、模块或技术决策 | `docs/ARCHITECTURE.md`、ADR |
| 表、字段、枚举、状态机 | `docs/DATA_MODEL_AND_WORKFLOW.md` |
| API、AI Schema、Tool | `docs/API_AI_TOOL_CONTRACTS.md` |
| 测试、指标、门禁 | `docs/TEST_AND_ACCEPTANCE.md` |
| 安全、权限、依赖、许可证 | `docs/SECURITY_AND_OPEN_SOURCE.md` |
| 里程碑、顺序、Entry/Exit Gate | `docs/IMPLEMENTATION_ROADMAP.md` |
| 仓库执行规则 | `AGENTS.md` 或 `docs/development/` |

不得在“最终结论”后继续追加正式规则，应合并到对应权威章节。

## 8. 任务拆分

单个任务应具有一个主要目标和可验证输出。

适合并行的工作：

- 不同只读调查；
- 不重叠文件的独立实现；
- 实现与独立测试审查；
- 文档链接检查与标识符比较。

不适合并行的工作：

- 同一模型和迁移；
- 同一入口文档的大规模重写；
- 有严格先后依赖的 Schema、Service、API；
- 会竞争相同生成文件的任务。

## 9. 验证策略

验证规模与风险成比例：

- 文档：链接、标识符、路径、命令、状态、行数、`git diff --check`；
- 局部后端：格式、静态类型、定向单元测试；
- 数据或迁移：空库、重复迁移、约束和回滚策略；
- 契约：OpenAPI、Schema 和 Tool contract；
- 前端：format、lint、build、必要的 Playwright；
- 基础设施和安全：clean-room；
- Agent：黄金集、注入、权限、审批和失败测试。

测试失败时不能删测试或降低门槛。必须修复、明确记录失败，或说明为何未运行。

## 10. 完成前检查

- 用户要求是否全部完成；
- 禁止范围是否未触碰；
- Git 差异是否只包含预期修改；
- 是否保留用户已有差异；
- 命令、路径和链接是否基于实际工程；
- 是否出现过时前端包管理器、Celery、迁移或初始化数据脚本引用；
- 稳定 ID、枚举、Schema、API、Tool 是否意外变化；
- 文档状态和许可证状态是否准确；
- 测试结果是否真实；
- 未解决问题是否明确列出。

## 11. 交付格式

交付应先说明结果，再说明验证和限制。建议包含：

```text
完成内容
关键修改
验证结果
数据库或契约变化
安全与可信边界
未完成或已知限制
Commit
```

没有创建 commit 时要说明原因，不能虚构 hash。用户看不到终端输出时，应转述关键数字和失败信息。
